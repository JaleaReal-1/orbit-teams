# Planificación de Orbit Soft

## 1. Visión del proyecto

Orbit Soft será un pequeño estudio de desarrollo de software orientado a estudiantes, docentes, profesionales independientes, emprendimientos y organizaciones de la UPeU filial Juliaca.

La empresa ofrecerá aplicaciones móviles, páginas web y sistemas personalizados a precios accesibles. El objetivo inicial no es construir una gran plataforma SaaS ni asumir costos de servidores, sino crear soluciones reutilizables que puedan adaptarse rápidamente a cada cliente.

La propuesta de valor es:

> Partimos de una solución base y la adaptamos a los procesos, necesidades y presupuesto de cada cliente.

El producto principal de Orbit Soft será la página informativa y comercial. Desde ella, los clientes podrán conocer las soluciones disponibles, revisar demos, elegir una plantilla y solicitar una adaptación.

## 7. Estrategia de aplicaciones móviles y funcionamiento offline

El celular será el dispositivo prioritario porque es el medio más utilizado por los estudiantes. La primera plataforma será Android, debido a su presencia entre los usuarios objetivo y a que permite distribuir aplicaciones directamente durante la etapa inicial.

### Aplicación Android

Para clientes que necesiten una aplicación Android más integrada, se podrá entregar un APK. Esta modalidad requiere explicar la instalación desde fuera de Play Store y definir un proceso de actualización.

### Datos locales

Las aplicaciones individuales pueden guardar la información en el teléfono mediante almacenamiento local o SQLite. Esto permite funcionar sin conexión a internet.

Adecuado para:

- Agendas personales.
- Seguimiento de cursos.
- Registro personal de pacientes.
- Control de gastos.
- Inventarios pequeños.
- Formularios y listas.

### Aplicaciones colaborativas

Cuando varios celulares necesitan consultar o modificar los mismos datos, se requiere sincronización. En ese momento se incorporará un backend y una base de datos central.

La diferencia debe explicarse al cliente:

- **Offline individual:** no necesita servidor y guarda datos en un dispositivo.
- **Multiusuario:** necesita sincronización y, normalmente, un servidor.

## 8. Estrategia de despliegue

### Etapa inicial

- Página comercial publicada gratuitamente.
- Aplicaciones móviles Android instaladas localmente o distribuidas como APK.
- SQLite para proyectos pequeños.
- Copias de seguridad exportables.
- Demos sin datos reales.
- Sin hosting propio para clientes.

### Red local

Si el cliente necesita varios equipos en un mismo local, la aplicación puede ejecutarse en una computadora principal y abrirse desde otros dispositivos conectados a la misma red Wi-Fi.

### Servicios gratuitos para demos

La página comercial puede publicarse en GitHub Pages o Cloudflare Pages. Las demos backend pueden probarse en una plataforma gratuita, siempre que no guarden datos importantes.

Los servicios gratuitos pueden suspender aplicaciones inactivas o no conservar archivos locales. No deben utilizarse para almacenar pacientes, inventarios o registros comerciales sin una base de datos y copias de seguridad adecuadas.

### Evolución futura

Migrar a un servidor cuando el cliente necesite:

- Acceso desde distintas ubicaciones.
- Varios usuarios simultáneos.
- Sincronización entre celulares.
- Copias de seguridad automáticas.
- Notificaciones centralizadas.
- Varias sucursales.
- Integraciones externas.

```text
│   ├── Servicios
│   ├── Plantillas
│   ├── Demos
│   └── Formulario de contacto
│
├── Aplicaciones móviles
│   ├── Campus Planner

│   ├── Clinic Pocket
│   ├── Agenda Local
│   ├── Inventory Mobile
│   └── Event Check-in
│
├── Núcleo reutilizable
│   ├── Usuarios y roles
│   ├── Organizaciones
│   ├── Configuración visual
│   ├── Reportes
│   ├── Exportaciones
│   └── Copias de seguridad
│
└── Backend futuro
    ├── API REST
    ├── Autenticación
    ├── Sincronización
    ├── PostgreSQL o MySQL
    └── Notificaciones
```

La interfaz, los datos locales y la sincronización deben mantenerse separados. Así una aplicación puede comenzar offline y migrar después a una API sin rehacer toda la interfaz.

## 10. Tecnología inicial sugerida

- Frontend comercial: HTML, CSS y JavaScript o React.
- Aplicaciones móviles: React Native, Flutter o Capacitor, según las funciones requeridas.
- Backend local: FastAPI.
- Base local: SQLite.
- Backend futuro: FastAPI con PostgreSQL o MySQL.
- Empaquetado: Docker para instalaciones reproducibles.
- Exportaciones: Excel y PDF.
- Comunicación: WhatsApp mediante enlaces y mensajes preparados.

No se deben guardar credenciales en el código ni usar datos reales en las demos.

## 13. Reglas de privacidad y operación

- No usar datos reales de pacientes o estudiantes en demos.
- Crear datos ficticios para capturas y videos.
- Entregar una política básica de privacidad.
- Explicar dónde se guardan los datos.
- Incluir copias de seguridad y restauración.
- Evitar contraseñas compartidas entre clientes.
- Documentar quién tiene acceso a cada sistema.
- No publicar bases de datos ni archivos de producción en GitHub.
- Mantener fuera del repositorio las claves, `.env`, certificados, fotos y bases locales.

## 16. Decisiones adoptadas para el MVP — 12 octubre 2026

Esta sección sustituye las decisiones pendientes y el próximo objetivo de las secciones 14–15 cuando difieran:

- Nombre confirmado: Orbit Soft; identidad oscura con acento verde, composición moderna para celular. Estudio independiente de la UPeU.
- Web comercial: HTML/CSS/JavaScript estáticos, sin backend comercial. Catálogo centralizado de ocho soluciones y fichas individuales renderizadas desde datos.
- Solicitud: formulario validado, mensaje revisable y envío manual mediante enlace WhatsApp; sin almacenamiento en servidor.
- Móvil: Capacitor 8 + Vite, proyecto Android generado y versionado. Primera plantilla Campus Planner. No PWA; APK con recursos empacados y funcionamiento local.
- Persistencia: Preferences nativo para un conjunto pequeño de datos (máximo 500 registros por módulo). Demo usa localStorage. Adaptador separado para migrar a SQLite si crece el volumen. No sincronización.
- Copias: JSON exportable y restaurable con validación, exportación CSV y compartir nativo Android. Sin cifrado propio; no introducir datos sensibles en las demos.
- Núcleo reutilizable: dominio, reportes, configuración visual y contratos opcionales de sesión/usuarios/roles. Autenticación real y colaboración continúan pendientes.
- Backend futuro: esqueleto FastAPI y conectores explícitos SQLAlchemy PostgreSQL/MySQL. No se despliega ni crea datos en esta fase.
- Referencias comerciales: web desde S/ 300, Campus Planner desde S/ 350; otras referencias/plazos en el catálogo. Son orientativas, el alcance debe cotizarse. Solo Campus Planner tiene demo funcional.
- Publicación autorizada: AWS en /home/ec2-user/orbit-soft; contenedor Nginx separado, ingreso HTTP por hostname/IP autorizados, preservando los servicios anteriores. Esta decisión sustituye la publicación gratuita externa del plan inicial. HTTPS propio requiere dominio/certificado y queda pendiente.
- Sin pagos, usuarios comerciales, panel administrativo ni hosting de clientes. La app no solicita permiso INTERNET y deshabilita backup automático Android.
- Generación y sincronización nativa comprobadas. Compilar, firmar e instalar APK en teléfono requiere JDK 21/SDK 36 no disponibles en este equipo; la comprobación nativa se documenta como pendiente, no como entrega realizada.

Siguientes pasos: verificar plantilla en teléfono Android, construir APK firmado, revisar referencias comerciales con un piloto y configurar dominio/HTTPS. La sincronización solo se habilitará con una necesidad concreta de compartir datos.
